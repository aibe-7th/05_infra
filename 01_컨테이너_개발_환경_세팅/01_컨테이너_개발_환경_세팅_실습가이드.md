# 컨테이너 개발 환경 세팅 통합 실습 가이드

## 1. 실습 개요 및 목표

본 실습은 클라우드 및 컨테이너 인프라 학습의 첫 단계로, 로컬 머신에서 Docker 컨테이너 런타임 환경을 점검하고 Ubuntu 최신 공식 LTS 이미지를 다운로드하여 대화형 컨테이너를 구동하고 제어하는 기본기를 확립합니다.

> 💡 **[핵심 원리]**
> - **Client-Server 아키텍처**: 사용자가 터미널에서 입력하는 `docker` 명령은 Docker Client(CLI)이며, 실제 컨테이너를 생성하고 이미지를 관리하는 주체는 백그라운드 데몬인 Moby 엔진(`dockerd`)입니다. 양단은 REST API 및 유닉스 도메인 소켓(`/var/run/docker.sock`)을 통해 통신합니다.
> - **커널 공유와 네임스페이스 격리**: 컨테이너는 가상 머신(VM)처럼 게스트 OS 커널 전체를 구동하지 않습니다. 호스트의 리눅스 커널을 직접 공유하되, Linux Namespaces(PID, NET, MNT, IPC, UTS)로 격리 공간을 생성하고 Control Groups(cgroups)로 하드웨어 리소스를 제한합니다.

### 핵심 학습 목표
1. Docker CLI와 백그라운드 Moby 엔진(`dockerd`) 간의 통신 상태 및 시스템 할당 자원을 점검한다.
2. 최신 공식 LTS 베이스 이미지인 `ubuntu:26.04`를 다운로드하고 이미지 메타데이터(크기, 아키텍처)를 검증한다.
3. 대화형(Interactive) 옵션을 사용하여 Ubuntu 컨테이너를 생성하고 내부 Bash 쉘에 진입한다.
4. 프로세스를 종료하지 않고 백그라운드로 안전하게 분리(Detach)한 후 `attach` 및 `exec`로 재접속하는 세션 제어 방식을 익힌다.

---

## 2. 실습 환경 및 준비

본 실습은 라이선스 제약이 없고 비용 부담이 전혀 없는 오픈소스 기반 환경인 **Rancher Desktop**을 표준 컨테이너 엔진으로 사용합니다.

- **호스트 작업 환경**: macOS 터미널, Linux Bash, Windows WSL2 / Git Bash
- **컨테이너 엔진**: Rancher Desktop (Container Engine 설정: `Moby (dockerd)`)
- **실습 베이스 이미지**: `ubuntu:26.04` (최신 공식 LTS 이미지)
- **실습 컨테이너 명칭**: `linux-practice`

> ⚠️ **[주의 사항]**
> - Rancher Desktop 실행 후 반드시 설정 메뉴(`Preferences > Container Engine`)에서 엔진 유형이 `Moby (dockerd)`로 선택되어 있는지 확인하십시오. (`containerd (nerdctl)` 모드인 경우 표준 `docker` CLI 명령과 소켓 경로가 다를 수 있습니다.)
> - Windows 사용자의 경우 WSL2 백엔드가 정상 구동 중이어야 하며, 터미널에서 `wsl --status` 명령으로 기본 배포판 가동을 점검합니다.

## 3. 실습 절차

### Step 1. Docker 엔진 연결 상태 점검

터미널을 열고 로컬 Docker CLI가 백그라운드 Moby(`dockerd`) 엔진과 정상적으로 통신하는지 점검합니다.

```bash
docker version
```

- **옵션 및 구문 설명**:
  - `docker version`: Client(CLI)와 Server(Engine)의 버전, Git 커밋, OS/아키텍처 정보를 동시에 조회합니다.

> 📌 **[기대 출력 확인]**
> ```text
> Client:
>  Version:           29.4.0
>  OS/Arch:           darwin/arm64 (또는 windows/amd64, linux/amd64)
> 
> Server: Docker Engine - Community
>  Engine:
>   Version:          29.4.0
>   OS/Arch:          linux/arm64 (또는 linux/amd64)
> ```
> `Client:` 및 `Server: Docker Engine` 블록이 모두 에러 없이 출력되어야 통신이 정상입니다.

---

### Step 2. Docker 시스템 자원 및 런타임 환경 상세 확인

현재 컨테이너 엔진에 할당된 하드웨어 리소스(CPU, 메모리)와 스토리지 드라이버 정보를 점검합니다.

```bash
docker info
```

- **옵션 및 구문 설명**:
  - `docker info`: 시스템 전체의 컨테이너/이미지 개수, 스토리지 드라이버, OS 종류, CPU 코어 수, 총 메모리 용량 등을 종합 출력합니다.

> 📌 **[기대 출력 확인]**
> ```text
> Server:
>  Containers: 0
>  Images: 0
>  Storage Driver: overlayfs (또는 overlay2)
>  Operating System: ...
>  CPUs: 12
>  Total Memory: 15.65GiB
> ```
> - `Storage Driver` 항목에 `overlay2` 또는 `overlayfs`가 표시되는지 확인합니다.
> - `CPUs` 및 `Total Memory` 항목을 통해 도커 VM에 정상적인 컴퓨팅 자원이 배정되었는지 확인합니다.

---

### Step 3. Ubuntu 26.04 LTS 공식 이미지 다운로드

리눅스 실습 환경으로 사용할 최신 공식 LTS 버전인 `ubuntu:26.04` 이미지를 원격 레지스트리(Docker Hub)에서 다운로드합니다.

```bash
docker pull ubuntu:26.04
```

- **옵션 및 구문 설명**:
  - `docker pull`: 원격 레지스트리에서 지정된 저장소와 태그의 이미지를 로컬 보관함으로 내려받습니다.
  - `ubuntu:26.04`: 공식 Ubuntu 리포지토리의 `26.04` LTS 태그 이미지를 지정합니다.

> 📌 **[기대 출력 확인]**
> ```text
> 26.04: Pulling from library/ubuntu
> 50914c2b24a1: Pull complete
> ed8299a102e9: Pull complete
> Digest: sha256:2260313b31c8c011cd2eebe728008efac1b3982be73eb71348ea2648d2c0e09b
> Status: Downloaded newer image for ubuntu:26.04
> docker.io/library/ubuntu:26.04
> ```
> 레이어 다운로드가 완료되고 최종적으로 `Status: Downloaded newer image for ubuntu:26.04`가 출력됩니다.

---

### Step 4. 로컬 도커 이미지 목록 및 메타데이터 검증

다운로드된 이미지의 식별 태그와 디스크 사용 용량, 아키텍처 정보를 확인합니다.

```bash
# 1. 로컬 저장소의 ubuntu 이미지 목록 필터링
docker images ubuntu

# 2. 이미지 아키텍처 조회
docker inspect --format='{{.Architecture}}' ubuntu:26.04
```

- **옵션 및 구문 설명**:
  - `docker images ubuntu`: 이미지명이 `ubuntu`인 로컬 이미지들의 태그, 이미지 ID, 생성 시기, 크기를 조회합니다.
  - `docker inspect --format='{{.Architecture}}'`: 이미지의 저수준 메타데이터 JSON 중 CPU 머신 아키텍처 필드만 파싱하여 출력합니다.

> 📌 **[기대 출력 확인]**
> ```text
> IMAGE          ID             DISK USAGE   CONTENT SIZE   EXTRA
> ubuntu:26.04   2260313b31c8        178MB         44.4MB        
> arm64 (또는 amd64)
> ```
> 최신 도커 환경에서는 `IMAGE` 통합 컬럼 표기 및 압축 해제된 실제 컨텐츠 크기(약 44MB 내외)가 출력됩니다. 아키텍처 메타데이터는 호스트 CPU에 맞추어 `arm64` 또는 `amd64`가 출력됩니다.

---

### Step 5. Ubuntu 대화형 컨테이너 생성 및 쉘 진입

다운로드한 이미지를 바탕으로 대화형(Interactive) 컨테이너를 생성하고 내부 Bash 쉘로 진입합니다.

```bash
docker run -it --name linux-practice ubuntu:26.04 bash
```

컨테이너 내부 진입 후 시스템 아키텍처와 OS 릴리즈 정보를 확인합니다:

```bash
uname -m
cat /etc/os-release
```

- **옵션 및 구문 설명**:
  - `docker run`: 새 컨테이너를 생성하고 시작하는 통합 명령어입니다.
  - `-i` (`--interactive`): 사용자의 표준 입력(stdin)을 유지하여 키보드 입력을 전달할 수 있게 합니다.
  - `-t` (`--tty`): 가상 터미널을 할당하여 리눅스 프롬프트를 정상 렌더링합니다.
  - `--name linux-practice`: 컨테이너의 고유 식별 이름을 부여합니다.
  - `ubuntu:26.04`: 실행할 베이스 이미지입니다.
  - `bash`: 컨테이너 진입 시 최초로 구동할 대화형 쉘 프로세스입니다.
  - `uname -m`: 컨테이너 내부 커널 머신 아키텍처를 조회합니다.

> 📌 **[기대 출력 확인]**
> ```text
> root@dca85abecf4b:/# uname -m
> aarch64 (또는 x86_64)
> root@dca85abecf4b:/# cat /etc/os-release
> PRETTY_NAME="Ubuntu 26.04 LTS"
> NAME="Ubuntu"
> VERSION_ID="26.04"
> VERSION="26.04 LTS (Resolute Raccoon)"
> ```
> 프롬프트가 `root@<container-id>:/#` 형태로 전환되고 리눅스 커널 아키텍처(`aarch64` 또는 `x86_64`)가 표시됩니다.

---

### Step 6. 컨테이너 백그라운드 전환 및 재접속 제어 검증

실행 중인 대화형 컨테이너를 종료하지 않고 백그라운드로 안전하게 분리(Detach)한 후, 상태 확인 및 재접속을 실습합니다.

```bash
# 1. 쉘 안에서 Ctrl 키를 누른 채 P와 Q를 순차적으로 입력 (Detach)
# 프롬프트가 호스트 머신 터미널로 복귀됩니다.

# 2. 컨테이너의 백그라운드 실행 상태 확인
docker ps

# 3. 백그라운드로 실행 중인 컨테이너의 포그라운드 쉘 스트림에 재접속
docker attach linux-practice

# 4. 재접속 확인 후 다시 Detach 처리 (Ctrl + P, Ctrl + Q 순차 입력)

# 5. 기존 메인 프로세스와 독립된 보조 쉘 프로세스를 추가 실행하여 진입
docker exec -it linux-practice bash

# 6. 보조 프로세스 세션 종료
exit

# 7. 메인 컨테이너 지속 구동 여부 확인
docker ps
```

- **옵션 및 구문 설명**:
  - `Ctrl + P, Ctrl + Q`: 포그라운드 프로세스를 종료하지 않고 세션을 분리(Detach)하는 Docker 터미널 이스케이프 시퀀스입니다.
  - `docker ps`: 현재 실행 중(`Up`)인 컨테이너 목록과 가동 시간(Status)을 확인합니다.
  - `docker attach linux-practice`: 실행 중인 컨테이너의 표준 입출력 스트림(PID 1 메인 프로세스)에 직접 연결합니다.
  - `docker exec -it linux-practice bash`: 메인 프로세스와 별개로 컨테이너 내부에 새로운 Bash 자식 프로세스를 추가 실행합니다.

> ⚠️ **[주의 사항]**
> - 포그라운드 대화형 세션이나 `docker attach`로 붙은 상태에서 `exit` 명령을 입력하거나 `Ctrl + D`를 누르면 컨테이너의 메인 프로세스(PID 1)가 종료되어 컨테이너 전체가 즉시 정지(`Exited`)됩니다.
> - 컨테이너를 종료하지 않고 호스트로 복귀하려면 반드시 `Ctrl + P, Ctrl + Q`를 순차 입력해야 합니다.
> - 반면 `docker exec`로 진입한 세션은 독립된 보조 프로세스이므로 `exit`를 입력해도 메인 컨테이너 수명 주기에는 영향을 주지 않고 안전하게 종료됩니다.

> 📌 **[기대 출력 확인]**
> ```text
> CONTAINER ID   IMAGE          COMMAND   CREATED         STATUS         PORTS     NAMES
> dca85abecf4b   ubuntu:26.04   "bash"    1 minute ago    Up 1 minute              linux-practice
> ```
> `docker ps` 실행 시 `STATUS` 열에 `Up ...` 상태로 `linux-practice`가 안정적으로 구동 중이어야 합니다.

## 4. 실무 트러블슈팅 가이드

실제 로컬 도커 엔진 검증(`04_proven/01_컨테이너_개발_환경_세팅.md`) 과정에서 확인된 핵심 오류 상황과 해결책입니다.

### 1) `Cannot connect to the Docker daemon` 오류
- **원인**: Docker Client(CLI)가 백그라운드 엔진 소켓(`/var/run/docker.sock`)에 접근하지 못하는 상태입니다.
- **해결책**:
  1. Rancher Desktop 애플리케이션이 백그라운드에서 완전히 부팅되었는지 확인합니다.
  2. `Preferences > Container Engine`에서 `Moby (dockerd)`가 선택되어 있는지 점검합니다.
  3. Windows의 경우 관리자 권한 PowerShell에서 `wsl --status`로 WSL2가 활성 상태인지 확인합니다.

### 2) `docker version` 출력 헤더 문자열 차이
- **원인**: 최신 Docker CLI(v24 이상)에서는 구형 문서와 달리 서버 영역 헤더가 `Server: Docker Engine - Community` 또는 `Server: Docker Engine` 형태로 다르게 표기될 수 있습니다.
- **해결책**: 헤더의 문자열이 완벽히 일치하지 않더라도 `Client` 블록과 `Server` 블록 양쪽에 Version 정보가 정상 노출되면 엔진 통신이 완벽한 상태입니다.

### 3) 스토리지 드라이버 명칭 차이 (`overlay2` vs `overlayfs`)
- **원인**: Docker 엔진과 containerd snapshotter 설정에 따라 `Storage Driver`가 `overlay2` 또는 `overlayfs`(`driver-type: io.containerd.snapshotter.v1`)로 표시됩니다.
- **해결책**: 두 드라이버 모두 리눅스 커널의 OverlayFS를 활용하는 표준 스토리지 드라이버이므로 정상 동작입니다.

### 4) 아키텍처 표기 불일치 (`arm64` vs `aarch64`)
- **원인**: `docker inspect` 메타데이터 조회 시에는 Docker/OCI 표준 규격인 `arm64`(또는 `amd64`)로 반환되지만, 컨테이너 내부에서 `uname -m`을 실행하면 리눅스 커널 표준 명칭인 `aarch64`(또는 `x86_64`)로 출력됩니다.
- **해결책**: 두 표기는 동일한 하드웨어 아키텍처를 의미하므로 정상입니다 (`arm64` ↔ `aarch64`, `amd64` ↔ `x86_64`).

### 5) `Ctrl + P, Ctrl + Q` 단축키가 동작하지 않는 현상
- **원인**: macOS 터미널, iTerm2, VS Code 통합 터미널 등에서 `Ctrl + P`가 이전 명령 히스토리 탐색이나 빠른 파일 열기(Quick Open) 전역 단축키로 먼저 가로채어져(Intercept) 컨테이너 TTY로 전달되지 않는 경우가 많습니다.
- **해결책**:
  1. 단축키 입력 후 반드시 호스트 터미널에서 `docker ps`를 실행하여 컨테이너가 `Up` 상태인지 확인합니다.
  2. 만약 빠져나오지 못해 `exit`를 입력하여 컨테이너가 정지되었다면, `docker start -ai linux-practice` 명령으로 언제든 다시 대화형 세션으로 재시작할 수 있습니다.
  3. 실무에서는 포그라운드 `run -it`보다 백그라운드 구동(`docker run -d -it ...`) 후 `docker exec -it ... bash`로 진입하는 제어 방식을 더 선호합니다.

## 5. 실습 자원 정리 (Cleanup)

실습이 끝난 후 호스트 터미널에서 구동 중인 컨테이너를 안전하게 중지하고 삭제하여 시스템 자원을 회수합니다.

```bash
# 1. 실행 중인 실습 컨테이너 중지
docker stop linux-practice

# 2. 중지된 실습 컨테이너 삭제
docker rm linux-practice

# 3. 잔여 컨테이너 목록 확인 (출력 결과가 비어 있어야 함)
docker ps -a
```

- **옵션 및 구문 설명**:
  - `docker stop`: 실행 중인 컨테이너 메인 프로세스에 `SIGTERM` 시그널을 보내어 정상 종료를 유도하고, 일정 시간 응답이 없으면 `SIGKILL`로 강제 정지합니다.
  - `docker rm`: 정지 상태인 컨테이너의 쓰기 계층과 메타데이터를 디스크에서 영구 삭제합니다.
  - `docker ps -a`: 중지된 컨테이너를 포함하여 시스템에 존재하는 모든 컨테이너 목록을 점검합니다.

> 💡 **[선택 사항: 다운로드된 베이스 이미지 삭제]**
> 디스크 공간을 확보하기 위해 실습에 사용된 베이스 이미지까지 완전히 제거하려면 다음 명령어를 수행합니다:
> ```bash
> docker rmi ubuntu:26.04
> ```
