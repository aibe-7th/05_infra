# 도커 이미지 빌드와 볼륨 네트워크 통합 실습 가이드

## 1. 실습 개요 및 목표

본 실습은 실제 프로덕션 수준의 Spring Boot 백엔드 애플리케이션(`simple-back`)을 컨테이너화(Dockerizing)하고, 12-Factor App 원칙에 입각한 환경변수 외부 주입, 가상 네트워크 격리 및 도커 내장 DNS 기반 서비스 디스커버리, 그리고 데이터 영속성을 위한 볼륨(Volume)과 바인드 마운트(Bind Mount)의 동작 메커니즘을 마스터하는 실습입니다.

> 💡 **[핵심 원리]**
> - **멀티 스테이지 빌드 (Multi-stage Build)**: 대용량 빌드 도구(JDK, Gradle)가 포함된 임시 빌더 컨테이너에서 소스코드를 컴파일하고, 최종 런타임 이미지에는 초경량 실행 환경(JRE)과 최종 실행 아티팩트(`JAR`)만 복사함으로써 이미지 용량을 80% 이상 줄이고 소스코드 유출 위험을 원천 차단합니다.
> - **불변 인프라 (Immutable Infrastructure) & 12-Factor App**: 데이터베이스 접속 주소, 계정, 포트 등 환경에 따라 달라지는 설정값은 이미지 내부에 하드코딩하지 않고 컨테이너 기동 시 환경변수(`-e` 또는 `--env-file`)로 주입합니다. 이를 통해 단 하나의 동일한 이미지를 개발, 테스트, 운영 환경에 수정 없이 배포할 수 있습니다.
> - **사용자 정의 네트워크와 내장 DNS (Service Discovery)**: Docker 사용자 정의 브리지 네트워크는 내장 DNS 서버(`127.0.0.11`)를 구동합니다. 동일 네트워크 상의 컨테이너들은 유동적인 사설 IP 대신 컨테이너 고유 식별 이름(`mysql-db`)을 호스트 도메인명으로 사용하여 외부 포트 개방 없이 안전하게 상호 통신할 수 있습니다.
> - **스토리지 생명 주기 분리**: 컨테이너의 쓰기 레이어는 휘발성이지만, Named Volume 및 Bind Mount는 호스트 스토리지에 데이터를 영구 저장하므로 컨테이너를 삭제하고 재생성해도 DB 데이터가 영구 보존됩니다.

### 핵심 학습 목표
1. 호스트 머신의 Gradle 빌드 산출물(`JAR`)을 복사하는 기본 Dockerfile을 작성하고 빌드 태그를 부여한다.
2. 호스트의 JDK나 빌드 도구 종속성을 배제하기 위해 빌더(`gradle:jdk17`)와 초경량 런타임(`azul/zulu-openjdk-alpine:17-jre-headless`)을 분리하는 멀티 스테이지 Dockerfile로 리팩토링한다.
3. 12-Factor App 원칙에 따라 민감한 데이터베이스 접속 자격 증명을 `-e` 옵션 및 실무 표준인 `--env-file` 방식으로 외부 주입한다.
4. 사용자 정의 브리지 네트워크(`app-net`)를 구성하여 컨테이너 간 내장 DNS 이름 해석을 검증하고, 명명된 볼륨(Named Volume)과 바인드 마운트(Bind Mount)의 영속성 메커니즘을 비교 실습한다.

## 2. 실습 환경 및 준비

본 실습은 실제 운영 중인 클린 아키텍처 기반의 Spring Boot 실습 프로젝트(`simple-back`)를 베이스로 진행합니다.

- **작업 디렉터리**: `~/workspace/simple-back` (Spring Boot 리포지토리 루트)
- **개발 언어 및 런타임**: JDK 17 (Eclipse Temurin 호환), Gradle 래퍼, Spring Boot 4.1.1
- **데이터베이스 환경**: 외부 클라우드 DBaaS (Aiven MySQL) 또는 로컬 `mysql:8.0` 컨테이너
- **가상 네트워크 및 스토리지**:
  - 사용자 정의 브리지 네트워크: `app-net`
  - 명명된 볼륨(Named Volume): `mysql-named-data`
  - 바인드 마운트(Bind Mount) 호스트 디렉터리: `~/workspace/simple-back/mysql-host-data`
- **사용 포트**: `8080` (Spring Boot), `3306` (MySQL)

> ⚠️ **[주의 사항: 런타임 베이스 이미지 표준]**
> - 본 실습의 멀티 스테이지 런타임 이미지는 **`azul/zulu-openjdk-alpine:17-jre-headless`**를 공식 표준으로 사용합니다.
> - `eclipse-temurin:17-jre-alpine`은 `linux/amd64` 아키텍처만 배포하여 Apple Silicon(arm64) Mac에서 `no match for platform in manifest: not found` 오류가 발생하지만, Azul Zulu Alpine은 `amd64`와 `arm64`를 모두 네이티브로 지원하여 124MB의 초경량 용량과 완벽한 크로스 아키텍처 실행을 보장합니다.

## 3. 실습 절차

### Step 1. 클론한 프로젝트 빌드 및 실행 JAR 생성

실습 베이스 프로젝트 `simple-back` 디렉터리로 이동하여 호스트의 Gradle 래퍼로 실행 가능한 `fat JAR` 아티팩트를 빌드합니다.

```bash
cd ~/workspace/simple-back
ls -la
./gradlew bootJar
ls -lh build/libs/
```

- **옵션 및 구문 설명**:
  - `./gradlew bootJar`: 스프링부트 애플리케이션의 소스코드와 종속 라이브러리를 하나로 패키징한 실행 가능 `fat JAR`를 생성합니다.

> 📌 **[기대 출력 확인]**
> ```text
> build/libs/simple-back-0.0.1-SNAPSHOT.jar (약 20~30MB 크기의 JAR 생성 확인)
> ```

---

### Step 2. 로컬 아티팩트 기반 1차 Dockerfile 작성 및 빌드

호스트에서 미리 빌드된 `JAR` 파일을 단순 복사하여 실행하는 1차 기본 `Dockerfile`을 작성하고 이미지를 빌드합니다.

```bash
cat <<'DOCKERFILE_EOF' > Dockerfile
FROM azul/zulu-openjdk-alpine:17-jre-headless
WORKDIR /app
COPY build/libs/*-SNAPSHOT.jar app.jar

ENV PORT=8080
ENV APP_MESSAGE="Hello from Artifact-based Dockerfile"

EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
DOCKERFILE_EOF

# 버전(0.1)과 환경(dev) 태그를 동시에 부여하여 빌드
docker build -t my-spring-app:0.1 -t my-spring-app:dev .
docker images my-spring-app
```

- **옵션 및 구문 설명**:
  - `COPY build/libs/*-SNAPSHOT.jar app.jar`: 호스트의 빌드 산출물을 컨테이너 내부 작업 디렉터리로 복사합니다.
  - `-t my-spring-app:0.1 -t my-spring-app:dev`: 단일 빌드 이미지 ID에 버전 태그(`0.1`)와 개발용 환경 태그(`dev`)를 동시에 부여합니다.
  - `.`: Docker 빌드 컨텍스트(호스트 기준 경로)를 의미합니다.

> 📌 **[기대 출력 확인]**
> ```text
> IMAGE               ID             DISK USAGE   CONTENT SIZE
> my-spring-app:0.1   da91e23a7d7c        124MB          124MB
> my-spring-app:dev   da91e23a7d7c        124MB          124MB
> ```
> `0.1`과 `dev` 두 태그가 동일한 IMAGE ID를 가리키며 출력됩니다.

---

### Step 3. 호스트 독립성을 위한 멀티 스테이지 Dockerfile 리팩토링

호스트 머신에 JDK나 Gradle이 설치되어 있지 않아도 컨테이너 엔진 자체에서 컴파일부터 패키징, 초경량 배포까지 완결하도록 멀티 스테이지(Multi-stage) 빌드로 전환합니다.

```bash
# 로컬 빌드 산출물 삭제 (호스트 환경 종속성 배제 확인)
./gradlew clean
rm -rf build/

cat <<'DOCKERFILE_EOF' > Dockerfile
# 1단계: 빌드 환경 (공식 Gradle & JDK 17 LTS 빌더)
FROM gradle:jdk17 AS builder
WORKDIR /workspace

# 의존성 캐시 최적화: 소스코드 변경 전 의존성 명세 스크립트 먼저 복사
COPY build.gradle settings.gradle .
RUN gradle dependencies --no-daemon || true

# 소스코드 복사 및 애플리케이션 빌드
COPY src src
RUN gradle bootJar --no-daemon

# 2단계: 실행 환경 (초경량 Alpine 기반 JRE 17 LTS 런타임)
FROM azul/zulu-openjdk-alpine:17-jre-headless
WORKDIR /app

# 빌드 스테이지에서 최종 패키징된 JAR만 복사 (빌드 도구 및 소스코드 제외)
COPY --from=builder /workspace/build/libs/*-SNAPSHOT.jar app.jar

ENV PORT=8080

EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
DOCKERFILE_EOF

# 1.0 정식 버전과 운영(prod) 환경 태그를 동시에 매핑하여 빌드
docker build -t my-spring-app:1.0 -t my-spring-app:prod .
docker images my-spring-app
```

- **옵션 및 구문 설명**:
  - `FROM gradle:jdk17 AS builder`: 빌드 도구가 포함된 1단계 임시 빌더 컨테이너를 정의합니다.
  - `COPY --from=builder ... app.jar`: 빌더 단계에서 컴파일된 산출물 파일만 2단계 최종 런타임 이미지로 복사합니다.
  - `FROM azul/zulu-openjdk-alpine:17-jre-headless`: 최종 런타임으로 초경량 Alpine JRE 이미지를 채택하여 빌드 도구가 포함된 이미지 대비 용량을 획기적으로 줄입니다.

> 📌 **[기대 출력 확인]**
> ```text
> my-spring-app:1.0    da91e23a7d7c    CONTENT SIZE: 124MB
> my-spring-app:prod   da91e23a7d7c    CONTENT SIZE: 124MB
> ```
> 호스트의 `build/` 디렉터리가 비어 있는 상태에서도 컨테이너 내부에서 독자적으로 빌드가 완료되고 실행 이미지가 생성됩니다.

### Step 4. 외부 클라우드 DBaaS(Aiven) 환경변수 직접(-e) 주입 연동

외부 클라우드 DBaaS(Aiven MySQL)의 엔드포인트와 접속 정보를 `-e` 옵션으로 직접 전달하여 컨테이너를 구동하고 연결을 검증합니다.

```bash
export AIVEN_URL="jdbc:mysql://<호스트이름>:<포트>/defaultdb?sslmode=REQUIRED"
export AIVEN_USER="avnadmin"
export AIVEN_PASSWORD="실제_Aiven_암호"

docker run -d --name spring-cloud-db -p 8080:8080   -e SPRING_DATASOURCE_URL="$AIVEN_URL"   -e SPRING_DATASOURCE_USERNAME="$AIVEN_USER"   -e SPRING_DATASOURCE_PASSWORD="$AIVEN_PASSWORD"   -e APP_MESSAGE="Connected to External Cloud DBaaS (Aiven) via -e!"   my-spring-app:1.0

docker ps
docker logs spring-cloud-db | grep "HikariPool"
curl -i http://localhost:8080/users
docker stop spring-cloud-db && docker rm spring-cloud-db
```

- **옵션 및 구문 설명**:
  - `-d`: 컨테이너를 백그라운드 데몬 모드로 구동합니다.
  - `-p 8080:8080`: 호스트의 8080 포트를 컨테이너 내부의 8080 포트로 포워딩합니다.
  - `-e KEY=VALUE`: 컨테이너 내부 프로세스 환경변수로 주입합니다.

> 📌 **[기대 출력 확인]**
> ```text
> HikariPool-1 - Start completed.
> Started SimpleBackApplication in 1.903 seconds
> HTTP/1.1 200 OK
> [{"id":1,"name":"infra-admin","email":"admin@example.com"}]
> ```

### Step 5. 실무 표준 --env-file 기반 환경변수 일괄 주입 전환

명령줄 히스토리에 자격 증명이 평문으로 노출되는 보안 위험을 방지하기 위해 환경설정 파일(`aiven.env`)을 생성하고 `--env-file` 옵션으로 전환합니다.

```bash
cat <<'ENV_EOF' > aiven.env
PORT=8080
APP_MESSAGE=Connected to External Cloud DBaaS via --env-file!
SPRING_DATASOURCE_URL=jdbc:mysql://<호스트이름>:<포트>/defaultdb?sslmode=REQUIRED
SPRING_DATASOURCE_USERNAME=avnadmin
SPRING_DATASOURCE_PASSWORD=실제_Aiven_암호
ENV_EOF

docker run -d --name spring-cloud-db -p 8080:8080   --env-file aiven.env   my-spring-app:1.0

docker ps
curl -i http://localhost:8080/users
docker stop spring-cloud-db && docker rm spring-cloud-db
```

- **옵션 및 구문 설명**:
  - `--env-file aiven.env`: 파일에 정의된 모든 환경변수를 컨테이너 프로세스 실행 시 일괄 로드합니다.

> 📌 **[기대 출력 확인]**
> 컨테이너가 정상 기동되고 `curl -i http://localhost:8080/users` 호출 시 정상적인 HTTP 200 응답과 JSON 데이터가 반환됩니다.

### Step 6. 사용자 정의 네트워크와 명명된 볼륨(Named Volume) 실습

외부 클라우드 DB 대신 로컬 컨테이너 간 통신을 위해 전용 브리지 네트워크(`app-net`)와 Docker 관리형 명명 볼륨(`mysql-named-data`)을 생성합니다.

```bash
# 1. 사용자 정의 브리지 네트워크 생성
docker network create app-net

# 2. 명명된 볼륨(Named Volume) 생성
docker volume create mysql-named-data

# 3. 명명된 볼륨을 마운트하여 MySQL 컨테이너 구동
docker run -d --name mysql-named   -e MYSQL_ROOT_PASSWORD=rootpass   -e MYSQL_DATABASE=mydb   -v mysql-named-data:/var/lib/mysql   mysql:8.0

# 4. MySQL 구동 확인 및 점검
docker logs mysql-named | grep "ready for connections"
docker stop mysql-named && docker rm mysql-named

# 5. 컨테이너 삭제 후에도 볼륨이 보존되는지 확인
docker volume ls
docker volume inspect mysql-named-data
```

- **옵션 및 구문 설명**:
  - `docker network create app-net`: 컨테이너 간 이름 기반 DNS 서비스 디스커버리를 지원하는 사설 가상 네트워크를 생성합니다.
  - `docker volume create mysql-named-data`: Docker 데몬이 관리하는 영속 데이터 볼륨을 생성합니다.
  - `-v mysql-named-data:/var/lib/mysql`: 볼륨을 컨테이너 내부 MySQL 데이터 저장 경로에 마운트합니다.

> 📌 **[기대 출력 확인]**
> ```text
> [
>     {
>         "Driver": "local",
>         "Mountpoint": "/var/lib/docker/volumes/mysql-named-data/_data",
>         "Name": "mysql-named-data",
>         "Scope": "local"
>     }
> ]
> ```
> 컨테이너를 삭제해도 `docker volume ls`에 `mysql-named-data`가 안전하게 보존되어 있음을 확인합니다.

### Step 7. 바인드 마운트(Bind Mount) 및 백그라운드 DB 프로세스 제어

호스트 파일 시스템 디렉터리를 직접 컨테이너에 연결하는 바인드 마운트 방식을 구성하고, 백그라운드 DB 내부에서 SQL 명령을 직접 실행합니다.

```bash
# 1. 호스트 마운트용 디렉터리 생성 및 바인드 마운트 MySQL 구동
mkdir -p ~/workspace/simple-back/mysql-host-data
docker run -d --name mysql-db   --network app-net   -e MYSQL_ROOT_PASSWORD=rootpass   -e MYSQL_DATABASE=mydb   -v ~/workspace/simple-back/mysql-host-data:/var/lib/mysql   mysql:8.0

# 2. 실시간 로그 스트리밍 확인 (ready for connections 및 port: 3306 확인 후 Ctrl + C)
docker logs -f mysql-db

# 3. 호스트 디렉터리에 생성된 실제 물리 파일 확인
ls -la ~/workspace/simple-back/mysql-host-data/

# 4. 백그라운드 MySQL 내부 쿼리 직접 실행
docker exec -it mysql-db mysql -uroot -prootpass -e "SHOW DATABASES;"
```

- **옵션 및 구문 설명**:
  - `-v ~/workspace/simple-back/mysql-host-data:/var/lib/mysql`: 호스트 디렉터리와 컨테이너 경로를 1:1로 실시간 마운트합니다.
  - `--network app-net`: 컨테이너를 생성한 사설망에 연결합니다.
  - `docker exec -it mysql-db mysql ...`: 실행 중인 컨테이너 내부에 `mysql` 클라이언트를 실행하여 데이터베이스 목록을 조회합니다.

> 📌 **[기대 출력 확인]**
> 호스트의 `mysql-host-data/` 폴더에 `ibdata1`, `mydb/` 등의 물리 파일이 실시간 동기화되어 나타납니다.
> ```text
> Database
> information_schema
> mydb
> mysql

### Step 8. 로컬 MySQL 연동용 local.env 작성 및 Spring Boot 실행

로컬 MySQL 컨테이너를 가리키는 `local.env` 파일을 작성하고, 동일한 네트워크(`app-net`) 상에서 Spring Boot 컨테이너를 구동합니다.

```bash
cat <<'ENV_EOF' > local.env
PORT=8080
APP_MESSAGE=Switched to Local Docker MySQL via local.env!
SPRING_DATASOURCE_URL=jdbc:mysql://mysql-db:3306/mydb?useSSL=false&allowPublicKeyRetrieval=true
SPRING_DATASOURCE_USERNAME=root
SPRING_DATASOURCE_PASSWORD=rootpass
ENV_EOF

docker run -d --name spring-app   --network app-net   -p 8080:8080   --env-file local.env   my-spring-app:1.0

docker ps
```

- **옵션 및 구문 설명**:
  - `SPRING_DATASOURCE_URL=jdbc:mysql://mysql-db:3306/mydb`: 호스트 IP 대신 컨테이너 식별자(`mysql-db`)를 도메인으로 지정합니다.
  - `--network app-net`: Docker 내장 DNS(`127.0.0.11`)가 `mysql-db`를 해당 컨테이너의 사설 IP로 자동 해석합니다.

> 📌 **[기대 출력 확인]**
> `docker ps` 실행 시 `mysql-db`와 `spring-app` 두 컨테이너가 모두 `Up` 상태로 안정 구동되어야 합니다.

## 4. 실무 트러블슈팅 가이드

실제 로컬 도커 엔진 검증(`04_proven/03-1_도커_이미지_빌드와_볼륨_네트워크.md`) 과정에서 확인된 핵심 오류 상황과 해결책입니다.

### 1) Apple Silicon(arm64) 환경에서 Temurin Alpine 빌드 실패
- **증상**: `eclipse-temurin:17-jre-alpine` 베이스 이미지 빌드 시 `no match for platform in manifest: not found` 오류 발생.
- **원인**: Eclipse Temurin 공식 저장소는 JDK 17 Alpine 태그를 `linux/amd64` 전용으로만 배포하고 ARM64 빌드를 제공하지 않습니다. (Alpine 멀티 아키텍처는 JDK 21부터 제공됨)
- **해결책**: x86_64와 arm64를 모두 공식 지원하는 초경량 Alpine JRE인 **`azul/zulu-openjdk-alpine:17-jre-headless`**를 런타임 베이스 이미지로 채택하여 에뮬레이션 오버헤드 없이 네이티브로 완벽 구동합니다.

### 2) 호스트에 JDK 미설치 시 Step 1 빌드 실패
- **증상**: `./gradlew bootJar` 실행 시 `Unable to locate a Java Runtime` 오류 발생.
- **원인**: 호스트 환경에 로컬 JDK가 설치되어 있지 않으면 Gradle 래퍼가 단독으로 동작할 수 없습니다.
- **해결책**: 이것이 바로 Step 3에서 **멀티 스테이지 빌드**를 도입해야 하는 결정적인 이유입니다. 호스트에 JDK나 Gradle이 전혀 없어도 컨테이너 엔진(`FROM gradle:jdk17 AS builder`)이 독립적으로 빌드를 완결합니다.

### 3) 명명된 볼륨(Named Volume)의 마운트 경로 오해
- **원인**: `docker volume inspect` 실행 시 출력되는 `Mountpoint: "/var/lib/docker/volumes/.../_data"`는 호스트(macOS/Windows)의 파일 시스템 경로가 아니라 **도커 가상 머신(VM) 내부의 리눅스 경로**입니다.
- **해결책**: 호스트 탐색기(Finder)에서 직접 접근할 수 없으며, 호스트 디렉터리에서 물리 파일을 직접 보고 조작하려면 Step 7의 **바인드 마운트(Bind Mount)** 방식을 사용해야 합니다.

### 4) MySQL 초기화 로그의 `port: 0`
- **원인**: MySQL 컨테이너 최초 기동 시 데이터베이스 초기화(Init) 과정에서 `ready for connections ... port: 0` 로그가 일시적으로 출력된 후 재시작되어 서비스 포트인 `port: 3306`으로 열립니다.
- **해결책**: `docker logs mysql-db`에서 `port: 3306` 로그가 최종 출력될 때까지 대기한 후 Spring Boot 컨테이너를 구동해야 커넥션 거부 에러를 방지할 수 있습니다.

### 5) 비대화형 환경에서 `docker exec -it` 실행 시 에러
- **원인**: 쉘 스크립트나 CI/CD 파이프라인에서 `-t` 옵션을 사용하면 `the input device is not a TTY` 오류가 발생합니다.
- **해결책**: 자동화 스크립트에서는 가상 터미널 할당 옵션인 `-t`를 제외하고 표준 입력 유지만을 위한 `docker exec -i`를 사용해야 합니다.

### 6) `--env-file` 작성 시 따옴표 및 특수문자 취급 주의
- **원인**: `--env-file`은 쉘 파싱을 거치지 않으므로 `KEY="VALUE"`처럼 따옴표를 붙이면 따옴표 자체까지 값으로 취급되어 DB 인증에 실패합니다.
- **해결책**: 환경변수 파일 내부에서는 따옴표(`"`)를 절대 쓰지 않고 순수 텍스트(`KEY=VALUE`)로 작성해야 하며, URL에 포함된 앰퍼샌드(`&`) 등도 이스케이프할 필요 없이 그대로 기입합니다.
